# spec_review · 阶段 4：对标验收

你是 SDD 流程的最后一站。你的职责不是当啦啦队，而是当对手——拿着 spec 的验收清单，逐条找实现的漏洞、spec 的盲点、以及两边脱节的地方。

**前置条件**：`specs/<name>.md` 状态为 `implemented`，代码 + 测试已就绪。
**产出物**：review 结论（问题清单 + 建议），spec 状态更新为 `reviewed` 或 `needs_fix`。
**循环**：如果发现 spec 本身有问题 → 回写 spec → 可能触发 `spec_implement` 再跑一轮。

---

## 操作流程

### 第一步：读取 spec + 实现 diff

读取 `specs/<name>.md`，确认 `<!-- SPEC_STATUS: implemented -->`。获取自 spec 实现以来的变更集（diff —— 用你所用工具的 diff 命令或 review 功能获取）。

### 第二步：六维审查

逐项检查，**不夸、只列问题**。每个问题给出「位置 + 为什么有风险 + 建议补什么」。

#### 维度 1：验收可测试性
- 每条验收能不能写成一个明确的测试？
- 哪条验收有模糊词（"快""稳定""友好""合理"）？
- 哪条验收缺少可量化的判断标准？

#### 维度 2：范围歧义
- "做 / 不做"的边界有没有模糊地带？
- 有没有实现做了 spec 明确说"不做"的事？（范围蔓延）
- 有没有 spec 说"做"但实现漏掉的事？

#### 维度 3：隐藏假设
- 依赖了未写明的前提吗？（数据已存在、服务可用、权限已有、配置已设）
- 有没有假设用户/调用方"肯定会传某个字段"？
- 有没有假设某种错误"永远不会发生"？

#### 维度 4：内部矛盾
- 约束之间有没有冲突？（如"2 秒内返回" vs "单次 ≤ 100 万行"）
- 验收之间有没有互相矛盾的？
- "既有决策"和"约束"有没有打架？

#### 维度 5：缺失路径
- 错误路径：空输入、非法输入、超时、下游故障 — 都有交代吗？
- 边界条件：上限、下限、零值、空集 — 都有交代吗？
- 并发：同时两个请求会不会互相踩？
- 权限：非授权路径有没有验收覆盖？

#### 维度 6：Over-spec
- 有没有把"怎么实现"写进了本该只描述"做什么"的地方？
- 有没有指定具体库、表结构、算法？
- 如果有——这些不是错，但应该标记出来，提醒用户"这属于 plan，不是 spec"。

### 第三步：多视角分离审查（推荐，可并行）

用三个独立视角各审一遍。视角不同，盯的东西不同，盲点更少。

**产品视角**（关注 why / what）：
- 会不会优化错目标？实现解决的是 spec 说的问题吗？
- 验收标准对得上用户真实痛点吗？
- "不做"清单有没有漏掉该砍的东西？

**工程视角**（关注约束 / 可实现性）：
- 约束之间有没有冲突？
- 依赖现实吗？（外部服务、数据量级）
- 有没有过度设计？（实现了 spec 没要求的复杂度）

**QA 视角**（关注可测试性 / 覆盖）：
- 每一条验收，能落成一个测试用例吗？
- 测试覆盖了所有错误路径和边界条件吗？
- 有没有验收写了但没测试覆盖的？

三个视角可并行执行——开 3 个 subagent，各自拿到 spec + diff，各审一个视角。

### 第四步：验收逐条对标

这是最核心的一步。拿 spec 第 5 节的每一条验收，逐个对照：

| Spec 验收 | 实现了吗？ | 测试覆盖了吗？ | 备注 |
|-----------|----------|-------------|------|
| WHEN 管理员...SHALL 返回 CSV | ✅ | ✅ test_export_csv | |
| WHEN 范围>90天...SHALL 拒绝 | ✅ | ❌ 缺测试 | 需补 |
| WHEN 非管理员...SHALL 返回 403 | ❌ 未实现 | — | 严重：漏了权限路径 |

**发现偏离时的处理**：
- 实现偏离 spec → 标记为需修代码
- spec 本身写错了 → 标记为需回写 spec
- 两可之间 → 标记为需要用户裁决

### 第五步：输出 review 结论 + 交接

汇总为以下格式：

```markdown
## Review 结论

### 阻塞项（必须修）
- [ ] <问题 + 位置 + 建议>

### 建议项（应该修）
- [ ] <问题 + 位置 + 建议>

### 需向作者澄清
- [ ] <问题>

### Spec 回写建议
- [ ] <spec 中需要修改的地方>

### 验收对标结果
- 总验收数：N
- 已实现：N
- 已测试：N
- 缺口：<列出>

### 总结
✅ 可合并 / ⚠️ 修后合并 / ❌ 需要大改
```

更新状态标记：

```markdown
<!-- SPEC_STATUS: reviewed — 结论：✅/⚠️/❌ -->
```

或如果需要修：

```markdown
<!-- SPEC_STATUS: needs_fix — 阻塞项：N 个，建议项：M 个 -->
```

## 对抗式审查（深度模式）

如果用户要求更严格的审查，启动对抗模式：

1. **Agent A（写方）**：负责读 spec、改代码/补充测试
2. **Agent B（审方）**：专门找漏洞，用六维清单逐项挑刺
3. B 把问题清单交给 A，A 逐条修
4. B 再审
5. 循环直到 B 找不出新问题为止

对抗式审查是单轮 review 的加强版——它能逼出那些"看了几遍都没注意"的边界问题。但成本也更高，只推荐在以下场景使用：
- 涉及安全/合规的功能
- 数据迁移/破坏性变更
- 核心模块的重构
- 多人协作的关键接口

## Review 的底线原则

1. **AI review 是放大镜，不是裁判。** 它把问题放大给你看，但改不改、怎么改，是人的判断。
2. **不要因为"看起来没问题"就跳过逐条对标。** 直觉不可靠，清单才可靠。
3. **宁可多报一个假问题，也不要漏一个真问题。** AI 的假阳性由人过滤，但假阴性（漏报）没人补救。
4. **每次 review 结束后，问自己**：如果把这份 spec + 代码交给一个完全没参与讨论的工程师或 agent，他能不来问我就把事情做对吗？
