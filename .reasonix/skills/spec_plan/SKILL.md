# spec_plan · 阶段 2：映射到实现计划

你是 SDD 流程的第三站。你的职责是把 `spec_write` 定稿的 spec，转化为一份可执行、可 review、可回滚的实现计划。

**前置条件**：`specs/<name>.md` 存在，且 `<!-- SPEC_STATUS: written -->`。
**产出物**：实现计划（可追加到 spec.md 的「任务拆解」节，或独立 `specs/<name>-plan.md`）。
**下游**：完成后交给 `spec_implement` 按计划小步落地。

---

## 操作流程

### 第一步：读取 spec，提取关键信息

读取 `specs/<name>.md`，确认 `<!-- SPEC_STATUS: written -->` 存在。从中提取：

- **范围（做 / 不做）**：决定要改哪些文件，不动哪些文件
- **约束**：决定技术选型的边界——只能用指定的语言/框架/库
- **既有决策**：避免重新评估已否决的方案
- **行为与验收**：每条验收对应到实现路径
- **任务拆解（如有初稿）**：作为计划的起点

### 第二步：只读调研代码库

**不要写任何代码**。先调研：

1. 找到相关文件：哪些模块、哪些文件会被改动
2. 理解现有模式：现有的路由/控制器/模型/中间件怎么写？照它的模式，不要另起风格
3. 识别依赖：任务之间有先后关系吗？哪些可以并行？
4. 标记风险点：改动范围内有没有测试覆盖薄弱的地方？有没有外部服务依赖？

输出调研摘要给用户确认：

```
## 调研摘要
- 涉及文件：<列出文件路径>
- 参考模式：<现有类似功能的实现，可作为模板>
- 依赖关系：<哪些任务必须先做>
- 风险点：<需要特别小心的地方>
```

### 第三步：产出实现计划

将 spec 的「任务拆解」和「行为与验收」展开为分步计划。每个步骤必须是：

- **有边界的**：改哪个文件、做什么，一步只做一件事
- **可独立验证的**：做完这一步，能跑什么命令验证它对了
- **可回滚的**：这一步出错，不影响其他步骤

格式：

```markdown
## 实现计划

### 步骤 1：<标题>
- 改动：`path/to/file.ts`
- 做什么：<具体描述>
- 验证：`<命令>` 或 <手动验证方法>
- 依赖：无 / 依赖步骤 N
- 风险：低/中/高 — <原因>

### 步骤 2：<标题>
...
```

**排序原则**：
- 先做不依赖他人的基础件（模型、工具函数）
- 再做依赖基础件的中间件（校验、权限）
- 然后做主流程（业务逻辑）
- 最后做错误路径 + 边界条件
- 测试贯穿始终——每条验收对应一个测试步骤

**并行标注**：标记哪些步骤可以并行执行（互不依赖），供 `spec_implement` 阶段用 subagent 并行处理。

### 第四步：人审计划

计划产出后，请用户逐条确认。这是**拦截"AI 想偏了"成本最低的关卡**——改计划远比改代码便宜。

重点让用户确认：
1. 文件路径对吗？有没有遗漏该改的文件？
2. 任务顺序对吗？依赖标注准确吗？
3. 风险标注对吗？有没有低估/高估的地方？
4. 验证方法可执行吗？命令能跑吗？

修改到用户说"确认计划"为止。

### 第五步：落盘 + 交接

将最终计划追加到 `specs/<name>.md` 的「任务拆解」节，更新状态标记：

```markdown
<!-- SPEC_STATUS: planned — 下一步：运行 spec_implement -->
```

告诉用户：

> 实现计划已就绪。下一步：运行 `spec_implement` 按计划小步落地。每完成一个步骤，回来更新完成状态。

---

## 计划粒度原则

| 场景 | 步骤粒度 | 示例 |
|------|---------|------|
| 绿地功能 | 每个步骤 = 一个可独立提交的文件/模块 | "新增 activity 查询接口路由" |
| 中大型迭代 | 每个步骤 = 一个文件的改动 | "在 permissions.ts 加导出权限校验" |
| 小改动 | 每个步骤 = 一段具体改动 | "在 export.ts 加行数预估逻辑" |

**不要**把整件事写成一个步骤——那等于没计划。
**不要**把每一步拆成一个函数——那是伪代码，不是计划。

---

## 风险标注参考

| 级别 | 含义 | 示例 |
|------|------|------|
| 低 | 纯新增，不碰现有逻辑 | 新增一个工具函数 |
| 中 | 修改现有逻辑，但影响范围可控 | 给现有中间件加一个分支 |
| 高 | 修改核心路径 / 数据模型 / 共享依赖 | 改 RBAC 校验逻辑、数据库 migration |
