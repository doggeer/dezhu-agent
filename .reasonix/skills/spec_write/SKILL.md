# spec_write · 阶段 1：定契约，生成结构化 spec

你是 SDD 流程的第二站。你的职责是把 `spec_brainstorm` 对齐的问题陈述，扩展为一份六要素齐全（或按场景合理裁减）的结构化 spec。

**前置条件**：`specs/<name>.md` 已存在 `## 1. 背景与目标` 和 `## 2. 范围（初稿）` 两节（来自 spec_brainstorm）。
**产出物**：同一份 `specs/<name>.md`，六要素补齐，验收标准可测试，状态标记为 `spec_written`。
**下游**：完成后交给 `spec_plan` 映射实现计划。

---

## 操作流程

### 第一步：读取上游输入

先读取 `specs/<name>.md`，确认 `<!-- SPEC_STATUS: brainstormed -->` 标记存在。如果不存在或文件为空：
- 告诉用户先运行 `spec_brainstorm`。
- **例外**：如果用户明确表示"已经想清楚了，直接写 spec"，则跳过 brainstorm 门禁。此时用户需口述背景、范围、约束，AI 据此起草六要素。

### 第二步：判断场景，决定六要素的裁减策略

不是每份 spec 都需要六节全写满。根据功能规模选择策略：

| 场景 | 结果与动机 | 范围边界 | 约束 | 既有决策 | 行为与验收 | 任务拆解 |
|------|-----------|---------|------|---------|-----------|---------|
| **绿地功能**（全新模块/系统） | ✅ 必写 | ✅ 必写 | ✅ 必写 | 🟡 留空声明 | ✅ 必写 | ✅ 必写 |
| **中大型迭代**（给现有模块加功能） | ✅ 必写 | ✅ 必写 | 🟡 只写新增/变更的约束 | ✅ 必写 | ✅ 必写 | ✅ 必写 |
| **小改动**（单文件、单接口变更） | 🟡 一句即可 | ✅ 必写 | ❌ 跳过 | ❌ 跳过 | ✅ 必写 | ❌ 在验收节末尾加一句实现备注即可 |
| **Bug fix**（行为修复） | ❌ 跳过 | ❌ 跳过 | ❌ 跳过 | ❌ 跳过 | ✅ 至少一条回归验收 | ❌ 跳过 |

> ✅ = 必写  |  🟡 = 视情况精简  |  ❌ = 可跳过

**向用户确认**：输出你判断的场景 + 裁减策略，让用户确认后再动笔。例如：

> 我判断这是「中大型迭代」。六要素中，「约束」只写本次新增的，「既有决策」请补充你已否决过的方案。「行为与验收」和「任务拆解」我会重点展开。这个策略可以吗？

### 第三步：AI 起草六要素

按以下模板逐节起草。起草时遵循 **"描述行为，不描述实现"** 原则：

---

```markdown
# Spec：<功能名称>

## 1. 背景与目标（Why）
<已有 — 来自 spec_brainstorm，可微调但不要大改>

## 2. 范围
### 做
- <具体、可验证的行为>
- ...

### 不做（Out of scope）
- <明确排除的东西 — 这是防范围蔓延最重要的一节>
- ...

## 3. 约束
- <技术栈约束：语言、框架、数据库 — 只写不可变的>
- <性能约束：延迟上限、吞吐量、并发数 — 有数字>
- <合规/安全红线：数据隐私、认证授权、审计>
- <向后兼容：不能破坏的现有行为>
- <不能碰的东西：哪些模块/接口/表不能改>

## 4. 既有决策
- <方案 X（已选定，理由：...）>
- <方案 Y（已否决，理由：...，下次评估条件：...）>

## 5. 行为与验收
<每条验收必须可测试。关键路径用 EARS 句式，次要验收用自由文本。>

### 正常路径
- WHEN <触发条件>，THE SYSTEM SHALL <明确响应>
- ...

### 异常路径
- WHEN <触发条件>，THE SYSTEM SHALL <错误行为>
- ...

### 边界条件
- WHEN <边界条件>，THE SYSTEM SHALL <预期行为>
- ...

## 6. 任务拆解
1. <有边界、可独立验证的子任务>
2. ...
3. <测试：覆盖第 5 节每一条验收>
```

---

### 第四步：人逐条定稿

起草完成后，逐节展示给用户，请用户逐条确认或修改。特别提醒用户检查：

1. **"不做"清单** — 有没有漏掉该排除的东西？
2. **约束** — 有没有漏掉合规/性能/兼容红线？
3. **既有决策** — 有没有被 AI 推翻的方案？
4. **验收标准** — 每一条能不能写成一个测试？有没有模糊词（"快""稳定""友好"）？

修改到用户说"定稿"为止，然后将 `<!-- SPEC_STATUS -->` 更新为：

```markdown
<!-- SPEC_STATUS: written — 下一步：运行 spec_plan -->
```

### 第五步：交接

告诉用户：

> Spec 已定稿，写入 `specs/<name>.md`。下一步：等待用户运行 `spec_plan` 映射到实现计划。如果后续实现中发现 spec 有误，记得回写这份文件 — 它是事实基准。

## EARS 判断启发式

不是所有验收都要用 EARS。判断方法：

**用 EARS（WHEN...THE SYSTEM SHALL...）的场景：**
- 涉及权限/角色（"管理员可以..."、"非管理员收到 403"）
- 涉及数据变更/持久化（"数据写入后..."）
- 涉及外部接口/API 契约（"接口返回..."）
- 涉及合规/审计（"必须记录审计日志"）
- 有明确触发条件和响应边界的任何行为

**用自由文本的场景：**
- UI 文案/样式（"按钮文案改为「确认导出」"）
- 纯格式调整（"CSV 用 UTF-8 BOM 编码"）
- 无需触发条件的静态约束（"字段 timestamp 使用 ISO 8601 格式"）
- 一句话能说清且无需测试的琐碎项

**判断准则**：问自己"这条验收能不能被一个不参与讨论的 QA 写成自动化测试？"——能，就用 EARS；不能，就细化到能力止。

## "描述行为，不描述实现"的正反例

| ❌ 实现化（不该写进 spec） | ✅ 行为化（该写进 spec） |
|---|---|
| 用 PostgreSQL 给 activity 表加索引 | 按 user_id + 时间范围查询活动，2 秒内返回结果 |
| 引入 Redis 缓存层 | 同一用户 1 分钟内重复查询返回缓存结果 |
| 用 Bull 队列异步处理 | 导出请求提交后立即返回，结果就绪后通知用户 |
| 给 users 表加 role 字段 | 仅管理员角色可执行导出操作 |
| 用 Passport.js 做 OAuth | 用户通过公司 SSO 登录后才能访问 |

**判断准则**：如果一句话指定了具体技术、库或表结构，它就属于 plan 阶段，不该写在 spec 里。Spec 只写"外部可观测的行为"。

---

## 约束的写法：要具体，不要抽象

| ❌ 太抽象 | ✅ 可验证 |
|---|---|
| 性能要好 | 单次导出 ≤ 50 万行，返回时间 ≤ 2 秒 |
| 安全第一 | 非管理员调用返回 403，每次导出写入审计日志 |
| 向后兼容 | 现有 API 响应格式不变，已有字段不删除、不改变类型 |
| 数据不能丢 | 导出行数 = 数据库查询行数，校验和匹配 |

---

## 快捷模式

如果用户直接给了一份接近完整的草稿，不需要从头起草。跳过第三步，直接进入第四步——审 + 改。但仍然要过一遍六要素清单，标记哪些节缺失或空洞。
